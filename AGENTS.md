# Agents Hestia

Hestia sert un foyer autonome. Amaury exprime le besoin, essaie Dev et donne un GO ou un non-GO ; il ne relit pas le code. Les preuves techniques et la revue sont la responsabilité des agents.

À chaque nouvelle tâche, lire [le workflow produit](docs/product-workflow.md) et [le protocole de reprise](docs/continuity.md), puis retrouver le travail courant depuis `artifacts/active-work.json` s'il existe. Vérifier ses références, les accords et l'état GitHub ; ne pas se fier au seul chat précédent ni déduire l'absence de travail d'un checkpoint manquant. Un seul besoin est approfondi à la fois. Les besoins futurs restent larges : le GO d'un brief ne déclenche aucun découpage ; les US apparaissent seulement pour le besoin engagé maintenant, une fois son cadrage complet et validé.

Avant tout développement et toute création de branche/worktree, lire [la clôture des lots](docs/lot-closure.md) et exécuter `node scripts/closure.mjs status`. Traiter les branches inconnues et les intégrations en attente ; un registre absent n'est pas un état vide. Employer les commandes encadrées pour démarrer et intégrer. L'agent demande l'accord manquant, effectue lui-même le merge autorisé après contrôles, puis vérifie intégration et préservation des sources avant nettoyage. Aucun lot ne disparaît du suivi par un simple « livré localement ».

Lire [la gouvernance de livraison](docs/delivery-governance.md), source de vérité des autorisations, preuves et revues. Utiliser le skill local [hestia-delivery](.agents/skills/hestia-delivery/SKILL.md) pour une modification livrable. Le skill réside dans `.agents/skills` : Codex découvre ses métadonnées puis lit son contenu à l'activation ; le routage explicite demeure pour les autres agents.

Pour clarifier un besoin, préparer un brief ou proposer un découpage, lire et utiliser le skill local [hestia-refinement](.agents/skills/hestia-refinement/SKILL.md). Il mène les échanges produit jusqu'aux Issues prêtes, puis passe le lot à `hestia-delivery`. Une validation du brief n'autorise pas sa publication : présenter le contenu exact des mutations GitHub et obtenir l'accord explicite applicable avant de les effectuer.

Avant tout développement, lire [la gouvernance de design](docs/design-governance.md), même si le lot paraît sans UI ; rappeler cette lecture dans chaque délégation de développement. La conception UI appartient exclusivement à Claude Design : les agents ne créent aucun écran, maquette ou composant visuel de leur propre conception, même provisoire. Ils remettent le prompt à Amaury, attendent son hand-off déposé à la racine et ne réalisent qu'une intégration technique fidèle dans un lot autorisé. Le Design System initial doit être validé, versionné puis réemployé à chaque nouvel écran. Un hand-off absent ou incomplet suspend la partie UI concernée et appelle un prompt complémentaire, jamais une UI de remplacement.

Avant toute création, révision ou remise d'un prompt Claude Design, lire [le protocole de qualification](docs/design/claude-design-workflow.md) et les sources officielles actuelles. La remise exige un dossier et une revue liés aux octets exacts, puis `node scripts/design-prompt.mjs check --dossier <dossier.json>` avec relecture réseau réussie. Aucune remise improvisée en chat, aucun ancien PASS ou audit CI hors ligne ne remplace ce contrôle. La création native d'un Design System est possible ; ne pas lui imposer les prérequis d'un autre parcours d'import. Consigner limites et prochaine action, sans promettre une qualité SOTA absolue.

- Inspecter l'état Git avant de modifier ; conserver tout travail existant. Pour cette seule fondation initiale, le travail dans ce dossier local est explicitement autorisé. Chaque lot ultérieur utilise une branche et un worktree isolés ; séparer aussi les chemins des auteurs concurrents.
- Préparer un contrat de tâche borné à partir de `harness/contracts/task-template.json`. Une tâche locale réversible déjà autorisée ne nécessite pas une nouvelle permission.
- Séparer conception, implémentation et revue. Déléguer les sous-tâches indépendantes avec des chemins possédés explicitement. Le relecteur indépendant reçoit un contexte propre et le candidat exact ; l'auteur ne s'auto-approuve pas.
- Exécuter les contrôles pertinents ; conserver les résultats réels, leurs limites et l'identité exacte du candidat. Un contrôle en échec, absent ou non exécuté ne vaut jamais PASS.
- Données synthétiques uniquement dans le dépôt, les tests et cette fondation. Ne jamais lire, copier ou transmettre des documents familiaux réels pour enrichir des fixtures. Ne jamais conserver de mots de passe, codes PIN ou cryptogrammes de cartes dans le profil familial.
- GitHub Issues et Projects constituent l'unique backlog. Les éventuels reçus d'import sont des preuves figées, jamais un suivi parallèle.
- Le dépôt public contient le produit installable et ses outils contributeurs. Toute automatisation privée d'animation, d'analyse d'activité ou de communication du projet appartient à un projet distinct, non public et sans accès au coffre familial.
- Deux environnements durables : Dev et Production. QA désigne des contrôles et une recette sur Dev. Aucun GO local ne vaut GO Dev ou GO Production.
- La publication du dépôt public `JeanZay/hestia` et la licence Apache-2.0 ont été explicitement autorisées le 12 septembre 2026 après la fondation locale. Cette autorisation couvre le code et les outils contributeurs, les Issues, le Project et les protections GitHub ; elle n'autorise aucun déploiement Dev ou Production, secret, donnée familiale ou coût supplémentaire. Elle n'autorise aucun lancement Claude par les agents. L'usage manuel de Claude Design par Amaury suit la gouvernance de design ; les contre-revues Claude de code suivent les règles distinctes de la gouvernance de livraison.
- Pendant un travail en cours, rendre la main avec une demande précise à Amaury : action, support/version, retour attendu et suite débloquée, en indiquant la priorité. Un bilan de faits ou « la suite est prête » ne suffit pas. Poursuivre soi-même les étapes pertinentes déjà autorisées ; respecter une pause ou une tâche réellement terminée sans créer de nouvelle demande artificielle.
- Terminer par les états datés « livré localement », « proposé pour GitHub », « bloqué » ou « différé », selon les preuves. Toute Production nécessite un GO explicite sur le candidat exact.

Ces consignes encadrent les agents ; elles ne constituent pas une barrière technique face à un acteur malveillant. Les hooks locaux sont volontaires ; vérifier les protections distantes effectivement configurées avant chaque intégration.
